# AI 공통 규칙과 Markdown 계획 승인 절차

버전: 1.0 · 모든 컴포넌트와 페이지 작업에 적용

**먼저 계획서를 작성하고, 사용자가 확인한 버전만 구현한다. 의문이 생기면 질문하고, 답을 얻기 전에는 의문에 의존하는 코드를 만들지 않는다.**

`docs/ai-design-system-spec.md`와 함께 적용한다. 이 규칙은 Button 한 개에 적용하는 수정 지시가 아니라 프로젝트 전체의 공통 계약이다. 새 컴포넌트·새 대화·다른 모델·수정 재요청에서도 다시 읽는다.

## 1. 두 단계의 작업

### 1단계: 분석과 계획서 작성

사용자가 Figma 구현을 요청하면 먼저 필요한 MCP 데이터와 기존 프로젝트의 API·토큰을 읽는다. `docs/templates/component-plan.md`를 사용해 `docs/plans/components/<Name>.md`를 만든다.

이 단계에서 허용하는 변경은 해당 계획서뿐이다. 컴포넌트·CSS·stories·토큰 입력·설정·새 패키지를 수정하지 않는다. 캐시 저장과 읽기 분석은 허용한다. 생성된 코드 초안이나 토큰 추천은 승인된 구현 계약으로 취급하지 않는다.

계획서에는 다음 세 종류를 구분한다.

| 구분 | 작성 방법 | 구현에 사용할 수 있나 |
|---|---|---|
| 확인한 사실 | Figma 노드·변수·asset 또는 코드 위치와 실제 값을 적음 | 계획 승인 후 가능 |
| AI의 해석 | 컴포넌트 역할·상태 의미·API 연결에 관한 해석과 근거·확신이 부족한 부분을 적음 | 사용자가 확정한 해석만 가능 |
| 미확정 질문 | 선택지·영향·필요한 답을 Q&A로 적음 | 답변 전에는 불가능 |

Figma에 Hover라는 이름이 있다는 사실과, 어느 영역에 어떤 이벤트로 Hover를 적용해야 한다는 해석은 다르다. 이름만 보고 모든 색·요소·링의 범위를 결정하지 않는다. 모든 Size × Variant × State 조합에 대해 실제로 읽은 범위와 읽지 못한 범위를 기록한다.

### 사용자의 확인과 수정

AI는 질문을 `ask_user_question` 선택지(한 번에 4개까지, 선택지 2~4개, 추천은 맨 앞 + "(Recommended)", 도구가 없으면 짧은 번호 목록)로 묻고, 핵심 해석과 정한 값을 대화창에 짧게 요약한 뒤 구현을 멈춘다. 학생에게 계획서 파일을 열거나 고치라고 하지 않는다. 사용자는 대화로 정정하고, 대화로 받은 결정은 AI가 계획서에 반영하고 바뀐 내용을 대화창에 보여 준다.

파일을 열었음, 파일 수정 시각 변경, 침묵, "좋네" 같은 일반 반응은 구현 승인으로 취급하지 않는다. 사용자가 승인 선택지 "Approve revision N"을 고르거나 "이 계획대로 진행해"라고 명시하면 그 버전의 구현을 허용한다. 같은 승인 버전에 대해 재승인을 요구하지 않는다.

AI는 사용자의 명시적 승인(선택지 또는 문장) 뒤에만 계획서의 `status: approved` 한 줄을 쓰고 다른 줄은 건드리지 않는다. 새 계획 파일을 처음부터 `status: approved`로 쓰지 않고, 승인된 계획을 바꿀 때는 같은 편집에서 `status: review-required`와 `revision` +1을 함께 쓴다(저장 전 훅이 막는다). 한 Figma 링크에 여러 부품이 있으면 `components: [Button, Link]` 계획 하나로 묶는다. 사용자 대신 고르거나 승인 명령을 실행하지 않는다. `open_questions`가 0이 아니거나 `facts_complete`가 false이면 구현을 시작하지 않는다. 숫자만 바꾸어 질문을 해결한 것처럼 만들지 않는다.

대화형 작업에서 사용자가 특정 revision의 진행을 명시했다면, 그 메시지를 승인 근거로 기록할 수 있다. 이것은 사용자 결정의 기록이며 AI 자체 승인이 아니다. 학생은 VS Code의 Qwen Code 확장에서 직접 승인·구현을 요청한다. Token Plan으로 모델을 호출하는 CLI·API·무인 실행을 대신 수행하지 않는다.

### 2단계: 승인 계획 구현

승인된 파일·revision·내용을 읽고 변경 범위를 고정한다. 확인된 역할·API·토큰·상태·아이콘·검증 목록만 구현한다. 계획의 내용은 구현 중에 몰래 고치지 않는다.

새 의문, 입력 충돌, 원본 변경, 없는 API, 부족한 토큰이 발견되면 영향을 받는 작업을 멈추고 Q&A를 진행한다. 답이 설계 계약을 바꾸면 revision을 올리고 `status: review-required`로 돌아가 새 버전을 확인받는다. 코드 내부의 동등한 구현 방식처럼 승인된 외관·API·동작을 바꾸지 않는 결정은 다시 승인받지 않아도 된다.

계획 승인과 결과 검수는 별개다. 계획대로 구현하고 검사를 통과한 컴포넌트는 `READY_FOR_REVIEW`이며, 학생/강사가 실제 화면·동작을 검수한 범위만 페이지의 카탈로그 부품으로 사용한다.

## 2. Q&A 규칙

질문은 해당 컴포넌트에 영향을 주는 결정만 묻는다. 이미 Figma·기존 API·사용자 결정에서 확인한 사실을 반복 질문하지 않는다.

```text
Q-01. 이 부품을 메뉴를 여는 Button으로 해석했습니다.
근거: 클릭 가능한 전체 영역과 오른쪽 화살표가 있습니다.
미확정: 누르면 메뉴가 열리는지, 목록 안에서 값을 선택하는 항목인지 알 수 없습니다.
어느 동작인가요?
A. 메뉴 열기
B. 목록의 값 선택
영향: 네이티브 역할, props, 키보드 동작과 stories가 달라집니다.
```

질문이 여러 개면 한 번에 모아 보여 준다. AI의 추천은 추천으로 표시하며 답변으로 확정하지 않는다. 답변은 질문 ID와 함께 계획서의 사용자 결정에 기록한다. 답하지 않은 질문은 열린 상태로 유지한다.

## 3. 모든 컴포넌트가 다시 확인할 공통 규칙

### R01 — 색 토큰은 값과 역할을 모두 대조

- 사용된 모든 fill·text·border·stroke·shadow 색과 alpha를 원본과 대조한다.
- Figma 원시 값 → primitive → semantic → 생성 CSS의 해석 값 → 실제 computed style을 추적한다.
- RGB가 같아도 alpha가 다르면 같은 색이 아니다. 값이 같아도 배경과 글자처럼 역할이 다르면 같은 토큰을 무조건 선택하지 않는다.
- 근사 색, 가장 가까운 토큰, 기존 색을 섞어 만든 대체색을 금지한다. 정확한 후보가 여러 개면 역할을 확인하고 불명확하면 질문한다.
- 매핑이 없으면 계획서에 없는 매핑으로 기록한다. 승인 전에 임의의 token 이름·역할을 확정하거나 토큰을 추가하지 않는다.
- 새 매핑은 정확한 원본 값과 승인된 역할을 근거로 입력 경로에서 만들고 CSS를 다시 생성한다. 생성물 직접 편집과 다른 부품이 쓰는 공용 역할의 재지정은 금지한다.

### R02 — 상태를 이름이 아니라 차이와 이벤트로 설명

- 각 Size × Variant × State의 노드 ID, 치수, 색, 테두리, 아이콘 유무와 위치, 글꼴 차이를 표로 적는다.
- 상태가 어느 요소에 적용되는지, 어떤 이벤트로 발생하는지, 무엇이 달라지는지 적는다.
- `Hover / Click / Focus`와 `Selected / Expanded / Checked`를 구분한다. 앞의 상호작용 의사 상태를 `state` prop으로 만들지 않는다. 뒤의 지속 상태는 원본과 공개 API에 근거해 모델링한다.
- 좌/우 상태, 그룹 Focus, 선택 아이콘, disabled 범위를 다른 컴포넌트에서 복사하지 않는다.
- Figma에 없는 시각 상태나 기존 상태를 복제한 스토리를 추가하지 않는다. 기본 접근성·네이티브 속성 전달은 별도 기능 계약으로 확인한다.

### R03 — 아이콘과 추가 상태를 임의 생성하지 않음

- 아이콘은 원본 asset/벡터 경로·크기·색·stroke·회전과 상태별 노출 조건을 기록한다.
- 같은 의미의 다른 SVG, 임의의 화살표/체크, placeholder 아이콘을 넣지 않는다.
- 원본에 아이콘이 없는 조합은 없음으로 명시한다. 모든 variant에 같은 아이콘을 자동 적용하지 않는다.
- asset을 읽지 못했다면 계획서에 누락으로 기록하고 질문한다. 읽지 못했다는 이유로 대체 그림을 만들지 않는다.

### R04 — 컴포넌트의 역할을 실제로 수행

Button은 클릭 콜백/form 동작, Input은 입력과 값 변경, 링크는 이동, 메뉴는 지정된 선택·열림/닫힘·키보드 계약을 수행한다. 역할이 불명확하면 먼저 질문한다. 외형·타입 검사·요소 존재만으로 기능 완료를 선언하지 않는다. disabled와 Tab/키보드 포커스도 해당 계약으로 확인한다.

### R05 — 동일 역할의 원본 재사용

새 부품 요청마다 기존 컴포넌트·API·stories를 조사한다. 기존 원본을 수정하거나 승인된 API로 조립한다. `NewButton`, 페이지 전용 복제 부품, 부품 내부 스타일을 덮어쓰는 임시 CSS를 금지한다. 다른 부품의 토큰·상태 계약을 이름만 바꿔 복사하지 않는다.

복합 컴포넌트의 요청 노드 바로 아래 인스턴스만 하위 부품으로 세며, 그 인스턴스 안의 인스턴스는 하위 부품 자체의 일부로 본다. 하위 인스턴스는 겉모습·크기·아이콘 유무가 아니라 Figma가 제공한 원본 컴포넌트/세트 이름으로 대응한다. 원본 이름이 정확히 하나의 기존 키트 부품과 일치할 때만 그 부품을 계획의 `Nested parts` 표에 기록하고, variant를 기존 prop으로 정확히 옮길 수 없으면 `ask`로 남긴다. 키트 부품이 아닌 것으로 사용자가 확정한 행은 만드는 방법과 함께 `none`으로 기록한다. 승인된 표의 키트 부품을 실제로 import·사용하며 다른 부품으로 바꿔치기하지 않는다.

복합 컴포넌트의 CSS는 하위 키트 부품의 `.ds-*` 클래스를 선택하지 않고, 하위 부품에 `style`·`className`을 넘겨 외관을 바꾸지 않는다. 배치는 복합 컴포넌트 자신의 `ds-<name>__*` 래퍼에 둔다. 공용 부품의 외관을 바꿔야 하면 그 원본을 별도 계획으로 수정하고 모든 사용처의 영향 범위를 확인한다. `ai:verify`에서 승인 표의 각 키트 부품 `data-testid`가 복합 루트 안에 실제 렌더되는지 확인하며, 하위 클릭이 복합 콜백으로 이어지는지 story `play`로 검사한다. 계획에 정한 경우에만 Tab 순서와 disabled 전파도 검사한다.

“복합 컴포넌트 안의 Button을 고쳐 줘”처럼 하위 부품 수정 요청이 오면 승인된 `Nested parts` 표가 가리키는 원본 키트 부품을 대상으로 삼는다. 공용 원본 수정은 그 부품을 쓰는 다른 컴포넌트와 페이지에도 영향을 줄 수 있음을 사용자에게 알리고 변경 범위를 확인받는다. 복제 부품이나 부모 컴포넌트의 내부 CSS 덮어쓰기로 영향을 숨기지 않는다.

### R06 — Storybook의 실제 렌더를 확인

투명 fill과 주변 배경을 분리하고 실제 iframe 전체 배경을 측정한다. 설정값만 적은 것을 적용 성공으로 취급하지 않는다. Matrix 상태 이름과 실제 화면이 일치해야 한다. 합성 `userEvent` 콜백 검사와 Playwright의 실제 포인터 의사 상태 검사를 구분한다. 타입·가드·렌더 검사와 원본 시각 대조를 각각 기록한다.

### R07 — 새 컴포넌트에서도 같은 규칙을 적용

- 작업 시작마다 이 문서의 버전과 적용한 규칙 ID를 계획서에 적는다. 이전 대화의 기억만으로 규칙을 적용했다고 보고하지 않는다.
- 사용자 정정이 공통 원칙인지 해당 부품의 사실인지 구분한다. "근사 색 금지"는 공통 규칙이고 "이 SplitButton의 링은 전체를 감싼다"는 해당 부품의 사실이다.
- 확인된 공통 정정은 이 문서와 스펙에 반영한다. 특정 부품에만 메모하고 끝내지 않는다. 사용자 결정이 없는 AI 제안을 공통 정책으로 승격하지 않는다.
- 공통 수정의 영향을 받는 기존 부품은 읽기 조사로 목록을 보고한다. 무관한 부품까지 임의로 수정하지 않는다.

### R08 — 디자인 시스템 토큰의 낭비를 방지

쓰이지 않는 semantic 토큰, 같은 역할·값의 중복 token, 승인된 출력과 관계없는 변수를 미리 만들지 않는다. 필요한 사용처·역할·정확한 값·기존 토큰으로 처리할 수 없는 이유를 계획서에 적는다. 값이 같아도 역할이 다른 token은 의미가 있으므로 무조건 합치지 않는다.

### R09 — LLM 토큰 사용량의 낭비를 방지

- 새 요청은 계획 단계 하나로 시작한다. 승인 전 코드 전체·중복 stories·여러 구현안을 생성하지 않는다.
- 성공한 MCP 응답과 읽은 파일은 작업 근거로 재사용하고, 빠진 상태·asset·변경된 자료만 추가 조회한다. 캐시를 최신 자료라고 단정하지 않는다.
- 전체 저장소·전체 토큰 목록·모든 SVG·Figma 참고 코드를 매 단계마다 출력하지 않는다. 상태·값·경로의 표를 사용하고 세부 자료는 필요할 때 읽는다.
- 관련 부품·사용처·토큰만 조사한다. 불명확한 설계로 구현→오류→재생성을 반복하지 않고 Q&A로 먼저 확정한다.
- 검사 재시도는 실패 원인과 바뀐 범위를 기록한다. 같은 실패를 변경 없이 반복하거나 임의의 스타일 변경으로 검사만 통과시키지 않는다.
- LLM 사용량을 보고할 때 실제 제공된 usage와 추정값을 구분한다. usage가 없으면 알 수 없음으로 보고한다.

## 4. Qwen Code 대화형 실행

학생은 VS Code의 Qwen Code 확장에서 Figma 요청 → 계획서 작성 → 선택지 Q&A → 대화창 요약 → 승인 선택("Approve revision N") → 구현 순서로 진행한다. 대화창 요약과 명시적 승인 없이 구현을 시작하지 않는다. 승인 전 컴포넌트를 구현하거나 자동 수정 루프를 시작하지 않는다.

사용자가 대화창에서 승인한 revision 가운데 `status: approved`, `facts_complete: true`, `open_questions: 0`인 것만 구현한다. 대화형 명시적 승인 기록은 1절의 절차를 따른다. AI가 사용자를 대신해 승인 상태를 확정하지 않는다.

계획의 대상 URL·revision·승인 상태·미해결 질문과 내용을 확인한다. 실행 중 계획 내용이 바뀌면 구현 결과를 완료로 처리하지 않는다. 계획 단계의 구현 파일 변경은 위반이다. `scripts/lib/component-plan.mjs`의 승인·해시·변경 범위 검사 함수는 유지하지만 이를 호출하던 무인 모델 실행 CLI는 제공하지 않는다. 모든 에이전트의 임의 파일 쓰기를 사전에 막는 보안 장치라고 설명하지 않는다.

이전 실행 결과를 현재 작업 완료 근거로 쓰지 않는다. 결과를 기록할 때는 현재 승인 계획·revision·내용 해시와 이번 실행의 근거를 연결한다. 기존 `.result.json`을 참조할 경우 `run_id`, `plan_hash`, `revision`, 결과 `status`, `open_questions`, `reason`이 현재 작업과 일치해야 한다. 질문이 남으면 차단 상태를 기록하며, 이 기록도 실제 자동 검사·원본 대조·사용자 검수의 대체 자료가 아니다.

입력 부족·새 질문·검사 실패가 남으면 사용자에게 돌아온다. 자동으로 같은 작업을 여러 번 요청해 비용을 쓰거나 계획을 넓히지 않는다. Token Plan은 사람이 공식 도구에서 대화형으로만 사용한다. 모델을 무인으로 호출하는 CLI·API·반복 실행은 금지한다.

Qwen Code의 write_file·edit·notebook_edit와 Claude Code의 Edit/Write hook은 해당 컴포넌트의 최신 계획이 미승인·미확정이면 쓰기를 차단한다. Stop hook은 계획/Q&A가 대기 중이면 자동 수정 재시도를 멈춘다. 셸 등 모든 변경 수단에 동일한 사전 차단이 적용된다고 주장하지 않는다.

페이지에도 계획 → 사용자 확인 → 조립 → 새 의문 Q&A 원칙을 적용한다. 페이지 계획은 `docs/plans/pages/<Name>.md`에 화면 명세·검수된 부품 매핑·배치·동작·질문을 작성한다. 현재 hook의 승인 계획 검사는 컴포넌트용이며, 페이지 계획의 기계적 검사는 별도 구현 범위다.

## 5. 계획서 승인 전 확인 목록

- [ ] 컴포넌트가 무엇인지와 수행할 역할이 확정됐다.
- [ ] 기존 원본 재사용과 변경 파일 범위가 정해졌다.
- [ ] 모든 구현 대상 상태·크기를 실제로 읽었다. 누락 상태가 없다.
- [ ] 색·alpha·token 값과 역할의 대응이 확정됐다.
- [ ] 아이콘의 원본과 상태별 유무가 확정됐다.
- [ ] props·동작·키보드·disabled 계약이 확정됐다.
- [ ] 계획에 근거 없는 variant·asset·대체색이 없다.
- [ ] 미해결 Q&A가 없고 실제 검증 방법이 정해졌다.
- [ ] 공통 규칙을 다른 컴포넌트에도 적용하는 것과 이 부품에만 적용할 사실을 구분했다.

AI가 위 항목을 채웠다는 사실과 사용자 승인은 별개다. 사용자의 답을 꾸며 계획을 승인하지 않는다.
